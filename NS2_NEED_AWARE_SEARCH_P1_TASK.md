## Shadow lifecycle

Предпочтительно после пользовательского terminal event. Это bounded best-effort диагностика:

- никаких пользовательских SSE/AG-UI events;
- answer/outcome неизменны;
- detached/unbounded работа запрещена;
- действует `NS_NEED_AWARE_EXTRA_BUDGET_MS`;
- cancellation учитывается насколько позволяет lifecycle;
- shadow failure не меняет пользовательский результат.

### Дополнения R2.1 по shadow

- Shadow после terminal event **не fire-and-forget**: задача должна быть зарегистрирована в существующем lifecycle / отслеживаемом наборе, иметь deadline `NS_NEED_AWARE_EXTRA_BUDGET_MS` и abort при остановке процесса.
- При `cancelled` / error запросе shadow не запускать (`cancelled` / `not_assessed`).
- Если bounded post-terminal невозможен — shadow выполнять **до synthesis**, не между answer и terminal event.
- Если request scope уничтожается сразу после terminal event и безопасный bounded запуск невозможен — выполнять shadow до terminal event, не меняя context/synthesis, отдельно измерить latency и записать отклонение в REPORT.

## NeedContract и assessment

### NeedContract

- P0/P1 NeedContract строится **детерминированно, без LLM**.
- Максимум 6 facets; required сохраняются первыми.
- При усечении: `facets_truncated=true`, `answer_full` запрещён.
- **Дополнение R2.1:** NeedContract использует из session только данные базового маршрута плюс explicit linked clarification answer из P2.

### Assessment state

`assessed` | `not_assessed` | `assessment_failed` | `skipped_direct` | `skipped_budget` | `cancelled` | `skipped_sample`

### Facet status

`supported` | `partial` | `missing` | `conflict` | `unknown` | `not_applicable`

### Gap reason

`not_retrieved` | `source_unavailable` | `coverage_unknown` | `version_unknown` | `ambiguous_entity` | `filtered_out` | `not_in_final_context` | `assessment_invalid` | `assessment_unavailable` | `budget_exhausted`

### Правила assessment

- Один пакетный LLM assessment call на стадию по всем открытым facets.
- Structural facets оценивать кодом.
- `assess1` только при non-empty allowed evidence и budget.
- `assess2` только new evidence target facets.
- **Дополнение R2.1:** LLM `assess1` запускается только при открытых non-structural facets, allowed textual evidence и budget. Assessment input при превышении budget режется в порядке существующего ranking.
- Пустой allowed evidence → LLM assessment не вызывать.

### Assessment I/O

**Input:**

- user question;
- facets: id / question / required / applicability;
- product/version constraints;
- allowed evidence с ID, revision metadata и точным текстом;
- не больше synthesis context budget.

**Output по facet:**

- status;
- reason_code;
- supporting/contradicting `evidence_id` + короткая exact quote.

### Валидация

- Валидировать кодом.
- Invalid JSON/schema → call `assessment_failed`.
- Unknown evidence ID, quote вне fragment, missing facet, запрещённый `not_applicable` → facet `unknown` / `assessment_invalid`.
- Quote normalization только: whitespace, quotes, ё/е, case.
- Retry/repair запрещены.
- Использовать существующий gateway client/parser.
- Extra facet IDs в assessment output игнорировать и фиксировать как нарушение; в `assess2` изменения non-target facets отклонять.
- `NS_NEED_AWARE_ASSESSMENT_TIMEOUT_MS=20000` — непроверенное допущение; live viability = `NOT_MEASURED`.
- **Дополнение R2.1:** P0 обязан включать реальный assessor adapter через существующий gateway client/parser; транспорт в tests заменяется stub по HC-3.

## GapPlanner и clarify

- GapPlanner deterministic. Один gap wave.
- Приоритет: required `conflict` / `missing` / `unknown` / `partial`, затем version/applicability.
- Optional gaps сами не запускают дорогой поиск, если ответ уже полезен.
- Gap retrieval стартует только если remaining budget покрывает retrieval + filter/gates + `assess2`; иначе `answer_partial` / `budget_exhausted`.
- Hub gap retrieval — только known product + одна target KB.
- FS-name — только literal exact name.
- Internal gap query строить из deterministic template; telemetry хранит template ID, не query text.

### Дополнения R2.1 по GapPlanner

- Не запускать retrieval для `unknown` из-за `assessment_invalid`, `assessment_unavailable` или `coverage_unknown`.
- `version_unknown` и `ambiguous_entity` → P1 `answer_partial`, P2 clarify.
- `source_unavailable` допускает поиск только в другом разрешённом доступном источнике.
- Remaining budget для gap wave считается по верхним границам:  
  `configured Hub timeout × planned physical calls + NS_NEED_AWARE_ASSESSMENT_TIMEOUT_MS`.

### Clarify

- **P1:** clarify только вычисляется, но пользователю отдаётся `answer_partial` с ambiguity.
- **P2:** максимум одно уточнение на исходный запрос, связанное explicit clarification ID; текст из template, без отдельной генерации; ответ сохраняется в session history.
- Не использовать эвристику «похоже на ответ».

## 0. Задание

Реализуй в существующем NS2 первый приоритет улучшения качества поиска:

> модель потребности → исходный поиск → карта доказательств → при необходимости одна адресная волна допоиска → один итоговый синтез либо прямой структурированный результат.

Нужен работающий вертикальный срез: серверная логика, совместимые контракты, минимальное отображение результата в интерфейсе, телеметрия, воспроизводимые тесты и отчёт. Не ограничивайся архитектурным описанием, заглушками или новым текстом системного промпта. Сначала изучи актуальную реализацию, затем расширь её минимально необходимыми изменениями.

**Цель:** ответ должен закрывать существенные аспекты задачи пользователя подтверждёнными сведениями. Когда сведений не хватает, система должна различать пробел в знаниях, неоднозначность вопроса, неизвестную применимость и отказ источника; выбирать адресный допоиск, полезный частичный ответ или одно уточнение, а не уверенно достраивать недостающее.

Это проверяемая гипотеза улучшения. Не обещай прирост качества до сравнения на размеченных запросах.

## 4. Модель потребности: NeedContract

Строй контракт по исходному вопросу, уже известным сведениям текущей сессии и существующему разбору намерения/продукта. Не добавляй отдельный обязательный LLM-вызов для планирования до поиска. Для первого среза используй текущий классификатор и небольшие типизированные шаблоны. Не представляй ограниченный набор регулярных выражений как универсальное понимание задачи; предусмотренные и неподдержанные случаи должны быть видны в тестах и отчёте.

> **Примечание R2.1:** session context → только разрешённый набор (базовый маршрут + explicit linked clarification answer из P2).

### Минимальное содержание контракта

- Версия схемы; тип задачи: `lookup`, `how_to`, `troubleshoot`, `impact`, `freshness`, `unknown`.
- Короткое описание нужного результата; продукт, версия и компонент, когда они известны.
- Для каждого ограничения — происхождение: явный запрос, подтверждённый контекст сессии или предположение. Явное уточнение пользователя имеет приоритет; конфликт нельзя молча разрешать в пользу старой сессии.
- Точные сущности: исходное написание и отдельно подтверждённая нормализация/алиас. Метод, путь API, таблицу, поле и код нельзя заменять «похожими».
- Не более шести существенных аспектов ответа — facets. Для каждого: стабильный ID, вопрос, обязательность, основание обязательности, подходящий вид доказательства и необходимые условия применимости.
- Неоднозначности, которые реально меняют ответ, и признак уже заданного уточнения в рамках этой задачи.

### Шаблоны по типу потребности

- «Найди описание операции X» — достаточно точного объекта и источника.
- «Как реализовать X» — могут быть обязательны механизм, существенные входные условия, ограничения и применимость.
- Диагностика — отделяй подтверждённые причины от гипотез и проверок.
- Влияние изменения — не обещай полноту зависимостей без данных о покрытии.
- Актуальность — различай версию продукта, ревизию документа и дату наблюдения источника.

Не требуй все аспекты всегда. Не придумывай неизвестную версию. Не меняй обязательность аспекта после поиска только потому, что доказательство не найдено. Неподдержанный тип задачи должен безопасно перейти в существующий поиск с `not_assessed`, а не получить фиктивно положительную оценку.

## 5. Карта доказательств: EvidenceAssessment

Сопоставляй аспекты не со всеми сырыми hits, а с доступными пользователю результатами, прошедшими штатную проверку допустимости источника и контекста. Наличие результата до фильтрации не означает наличие доказательства.

### Для каждого аспекта возвращай

- Статус: `supported`, `partial`, `missing`, `conflict`, `unknown` или `not_applicable`.
- Краткое основание статуса, без скрытой цепочки рассуждений.
- Ссылки на подтверждающие и противоречащие свидетельства.
- Отдельные сведения о доступности источника и применимости продукта/версии.
- Машиночитаемую причину пробела (см. канонический перечень gap reason в R2.1).

> **Примечание R2.1:** не использовать `assessment_failed` как gap reason из старого перечня R1; единый similarity/NLI threshold (в т.ч. 0.7) не заменяет assessment.

Каждое свидетельство должно ссылаться на реально переданный оценщику source/document/chunk ID, ревизию при наличии, раздел или структурированное поле. Для текста нужен проверяемый фрагмент/диапазон; для структурированных данных — существующий путь поля. Проверь, что цитата действительно содержится в исходном фрагменте и относится к нужной сущности. Ссылку, найденную только в ответе модели, не принимай.

`source_unavailable` не равно `missing`; пустая выдача не доказывает отсутствия возможности. Недоступность закрытого источника не должна раскрывать пользователю его существование. Дата успешного опроса каталога не равна дате загрузки или актуальности содержания.

Разделяй четыре проверки: допустимость источника, релевантность аспекту, подтверждение конкретного утверждения и применимость. Высокий similarity/NLI score, совпадение слова, заголовок или самоуверенность модели не заменяют эти проверки.

Структурированные точные сведения проверяй детерминированно. Для содержательного подтверждения по свободному тексту переиспользуй существующий семантический проверяющий компонент; при его отсутствии добавь ограниченный структурированный вызов существующего gateway. Нельзя выдавать keyword matching за проверку смыслового следования. Без работающей смысловой проверки допускается `unknown`/`partial`, но не фиктивный `supported`.

Ответ оценщика валидируй строгой схемой. Он не вправе менять исходную задачу, выбрасывать обязательные аспекты или возвращать произвольные команды/URL/SQL. Инструкции внутри документов — недоверенные данные, не инструкции исполнителю. Неизвестные IDs, неверные цитаты, невалидный JSON и невозможные переходы статусов отклоняй. Автоматических повторов и LLM-repair не добавляй.

`not_applicable` разрешён только по явному условию шаблона или подтверждённой применимости, а не по желанию оценщика сократить задачу. Противоречие фиксируй для сопоставимых сущностей, условий и версий; различие между двумя версиями само по себе не противоречие. Нельзя усреднить конфликт в высокий балл уверенности.

Итоговая достаточность вычисляется кодом: все обязательные применимые аспекты подтверждены и нет неразрешённого существенного конфликта/ограничения. Неизвестную обязательную применимость не считай подтверждённой. Различай состояние карты и гарантию конечного текста: достаточный контекст сам по себе не доказывает безошибочность генерации.

## 6. Адресный допоиск: GapPlanner

Планировщик получает контракт, карту, состояние источников и остаток бюджета. Он возвращает одно действие: `answer_full`, `answer_partial`, `retrieve_gap`, `clarify` или переход к существующему `no_context`.

Это внутренние решения, а не новые обязательные статусы жизненного цикла API. Сопоставь их с текущими контрактами и терминальными событиями.

`retrieve_gap` допустим только для конкретного обязательного пробела, который можно попытаться закрыть доступным источником. План содержит `facet_id`, допустимый канал, новый адресный запрос, фиксированные продукт/версию/точные имена и ожидаемый тип свидетельства. Используй шаблоны и существующие разрешённые адаптеры, без отдельного LLM-планировщика.

Приоритет имеет пробел, который мешает дать полезный ответ, а не уже хорошо покрытая тема. Не повторяй исходный запрос, не делай широкий повтор «найти ещё всё» и не трать бюджет на дубликаты. Допоиск не является retry после сбоя: запросы к заведомо недоступной/исчезнувшей базе повторно не отправляй. Допустим другой доступный и разрешённый источник, способный закрыть тот же аспект.

### Ограничения первой версии

- Не более одной волны допоиска и двух retrieval-операций в ней на пользовательский запрос.
- Не более двух дополнительных физических HTTP-вызовов Hub суммарно. Учитывай внутренний fan-out адаптеров: одна логическая операция не даёт права на десять вызовов.
- Дополнительные обращения к общим Hub/gateway выполняются последовательно. Не меняй существующий планировщик независимых локальных источников ради нового цикла.
- Максимум одна семантическая оценка после исходного поиска и одна повторная оценка после реально изменившегося набора доказательств. Повторная оценка — новая стадия, а не retry неудавшейся первой.
- Отдельных генераций промежуточного ответа нет; итоговый синтез максимум один. Все фактические вызовы, включая существующие классификаторы/NLI, учитываются в общей телеметрии; не скрывай их за названием адаптера.
- Таймаут/ошибка потребляют попытку. Никаких рекурсивных волн, повторной генерации, автоматического увеличения лимитов или обхода circuit breaker.

После допоиска заново примени обычные ACL, фильтры, ворота, квоты и дедупликацию. Оценщик не может воскресить отброшенный фрагмент или смешать каналы ради высокого покрытия. Сохрани полезные исходные доказательства, пока они допустимы и помещаются в контекст; новые сведения не вытесняют их просто из-за порядка получения.

Собери окончательный контекст с учётом аспектов: меньше дубликатов, больше разных необходимых доказательств. Повторно свяжи карту с реально оставшимися фрагментами. Доказательство, не вошедшее в конечный контекст и не доступное прямому структурированному renderer, не может подтверждать утверждение итогового ответа. Не заявляй семантическое подтверждение новых текстовых фрагментов, если повторная оценка не выполнена.

> **Примечание R2.1:** clarify в P1 отменён; P1 = `answer_partial` + ambiguity.

## 7. Уточнение и результат для пользователя

Уточняй только сведения, которые существенно меняют результат и не установлены из запроса, разрешённого контекста сессии или источников. На один исходный пользовательский запрос — максимум один вопрос. Сохраняй уже полученный ответ на уточнение и не задавай его заново без нового противоречия.

Если можно дать полезную подтверждённую часть, сначала отдай её, затем одно уточнение или конкретное ограничение. Не блокируй простой навигационный запрос анкетой о версии продукта. Не делай отсутствие неизвестного пользователю параметра обязательным препятствием для любой помощи.

Форма результата зависит от задачи:

- полный ответ — решение и ссылки, с существенными условиями;
- частичный — установленное и недостающее;
- недоступный источник — корректное ограничение проверки, не утверждение «этого не существует»;
- `no_context` и `fs_fresh` — действующее безопасное поведение и отсутствие лишней генерации.

Синтез получает исходный вопрос, контракт, только допустимый контекст и краткую валидированную карту. Неподтверждённые сведения нельзя представлять фактами. При диагностике гипотезы маркируются явно. Названия, коды и ссылки берутся из доказательств, а не из общего знания модели.

Используй существующую проверку имён/ссылок после синтеза. Новый универсальный постгенерационный LLM-судья в объём не входит. Ошибка проверки не должна запускать второй синтез: используй действующее безопасное ограничение/отклонение результата. Не выдавай неисправный текст за подтверждённый.

> **Примечание R2.1:** clarification только в P2; в P1 ambiguity → `answer_partial`.

## 8. Режимы, бюджеты и безопасный fallback

Добавь валидируемую настройку `off | shadow | active`. Имена и defaults — канон R2.1 (`NS_NEED_AWARE_*`). Default — `off`. Не включай функцию на пилоте и не изменяй действующий `.env` без отдельного указания. В примере конфигурации оставь безопасный default.

### Режимы

| Режим | Поведение |
| --- | --- |
| `off` | Текущий маршрут без нового оценщика, допоиска, изменения context/prompt/ответа и новых пользовательских событий. Регрессионными тестами доказать эквивалентность baseline. |
| `shadow` | Диагностика по правилам R2.1 lifecycle; без допоиска и без изменения пользовательского представления. |
| `active` | Карта для адресного допоиска и формирования результата в установленных пределах; clarify только с P2. |

### Настройки эксперимента (не измеренный SLA)

См. каноническую таблицу R2.1 выше.

Добавочный бюджет — общая монотонная deadline. Промежуточные таймауты ограничиваются её остатком и существующим общим deadline запроса, если он есть. Бюджет не сбрасывается на новой стадии. Базовые операции между стадиями тоже не продлевают эту deadline. Поздняя стадия может быть пропущена: не обязаны поместиться все максимумы одновременно.

Значение `0` должно реально отключать соответствующие дополнительные вызовы. Общие существующие лимиты остаются верхней границей; новая функция не расширяет их молча.

При ошибке построения/оценки/сохранения диагностики новый слой не должен превращать работавший запрос в 500. Сохрани базовый безопасный результат и явно зафиксируй `not_assessed` / `assessment_failed` в диагностике. Не называй fallback доказанно полным ответом. Не запускай для fallback повтор исходного поиска или второй синтез. Известные до ошибки ограничения не стирай.

## 9. Интеграция, контракт и наблюдаемость

Встрои проверку после первого отбора результатов, но до окончательного завершения `no_context`, чтобы активный режим мог сделать разрешённую попытку закрыть пробел. Исключение — действующие прямые ответы вроде D79, которые не надо искусственно ухудшать. Точную точку интеграции обоснуй по коду.

Сохрани жизненный цикл запроса, request/session IDs, отмену, историю и heartbeat. Отмена прерывает все новые операции через общий abort signal; после неё не допускаются запоздалый синтез, запись обычного `completed` или новые пользовательские события. Терминальное событие отправляется ровно один раз. Завершившиеся после timeout операции не могут обновить результат.

Дополнительные поля должны быть совместимыми: старые ответы и записи истории без quality-данных читаются штатно. Версию contracts изменяй по правилам проекта и собирай contracts перед API/web. Не создавай параллельную несовместимую модель ответа.

Минимальная телеметрия — см. раздел Telemetry в R2.1.

Используй существующую запись через единого писателя и собственную БД. Сначала рассмотри совместимое расширение текущего JSON payload. Если миграция действительно необходима — обосновать и сверить номера во всех активных worktree/branches. Применяй её только к подтверждённой изолированной тестовой NS2 БД. Недоступность такой БД — SKIP интеграционного теста, не разрешение идти в пилот.

Не сохраняй скрытую цепочку рассуждений. Не логируй целиком документы, приватную историю, текст внутренних запросов или диагностические ответы модели по умолчанию. Для наблюдаемости используй безопасные IDs, reason codes, счётчики и контролируемые краткие сведения. Результаты и persisted evidence должны сохранять существующие ограничения доступа. Недостающие ACL не придумывай: отметь блокер включения на пилоте и не расширяй доступ.

Все новые model prompts храни в репозитории, с версией и хэшем в диагностике. Следуй текущему стилю промптов. Предусмотри runtime-валидацию ответа; не доверяй модели управление лимитами, инструментами и правами.

## 10. Минимальный интерфейс

Без редизайна приложения добавь в active-ответ компактный блок «Что подтверждено / Что осталось уточнить» либо эквивалент в существующем дизайне. Он должен соответствовать конкретному ответу и окончательному контексту, а не глобальному здоровью всей системы.

Показывай понятные формулировки и доступные источники. Не показывай численную «уверенность 93%», если она не откалибрована; не называй достаточность контекста гарантией правильности ответа. Для простого точного поиска допускается отсутствие отдельного блока.

Одно уточнение можно отобразить как продолжение текущей сессии. Ошибка нового слоя не должна оставлять вечный spinner. Проверь старую историю без новых полей, off/shadow без изменений интерфейса, timeout, отмену и все терминальные исходы. Диагностические подробности не должны раскрывать скрытые источники или персональные данные.

> **Примечание R2.1:** блок только при `active` + `assessed`; при fallback скрывать.

## 11. Обязательные тесты

Сначала используй unit/integration тесты с управляемыми адаптерами и фикстурами. Новые тесты не должны обращаться в сеть по умолчанию. Синтетические данные должны явно называться синтетическими; не оформляй выдуманные операции как реальные API продуктов.

### Опорный end-to-end пример (синтетическая фикстура)

Пользователь: «Как изменить статус заявки в TEST_PRODUCT 1.0 и какие переходы разрешены?»

1. Исходный источник `demo-api-v1` подтверждает `PATCH /demo/requests/{id}/status` и обязательное поле `status`, но не допустимые переходы.
2. Контракт сохраняет продукт/версию и обязательный аспект переходов.
3. Карта отмечает этот аспект как `missing`, а не объявляет весь ответ готовым.
4. Планировщик делает адресный запрос только о переходах.
5. Источник `demo-rules-v1` с явной применимостью к TEST_PRODUCT 1.0 подтверждает переход `draft → active`.
6. После проверки и включения обоих свидетельств в окончательный контекст система делает один синтез.
7. Негатив: второй источник относится только к версии 2.0 → аспект версии 1.0 не закрывается, ответ частичный.
8. Вариант без второго результата не запускает новую волну.

### Checklist сценариев 1–24

Несколько проверок можно объединять в parameterized tests. Распределение по фазам — см. R2.1.

1. `off` эквивалентен исходному маршруту по выбору каналов, контексту, prompt и ответу при фиксированном генераторе; нет дополнительных сетевых вызовов.
2. `shadow` создаёт диагностику, но не меняет контекст, синтез, уточнения и UI; нет допоиска; дополнительная задержка измеряется отдельно.
3. Точный lookup и `fs_fresh` обходятся без нового семантического вызова; прямой результат D79 сохранён.
4. Полный исходный контекст: обязательные аспекты поддержаны, допоиска нет.
5. Один адресный пробел: поиск именно по нему, свидетельство найдено, карта обновлена, синтез один.
6. Нет результата допоиска: честный частичный ответ/`no_context`, третьей волны нет.
7. Несколько пробелов: максимум две retrieval-операции; одна волна; исчерпание общего бюджета останавливает новые стадии.
8. Fan-out адаптера не обходит лимит двух дополнительных HTTP-вызовов Hub; учитываются и ошибки/таймауты.
9. Неизвестный тип задачи либо неработающий семантический оценщик не получает фиктивного `supported`.
10. Технический идентификатор из вопроса не заменяется семантическим соседом или придуманным алиасом.
11. Неизвестная версия и явное противоречие с сессией не превращаются в подстановку последней версии.
12. Различные версии не считаются конфликтом автоматически; сопоставимые противоречащие источники не объединяются в уверенный ответ.
13. Источник недоступен/KB исчезла: нет вывода «возможности нет», нет бессмысленного retry той же базы.
14. Project panel и отдельный канал ФС не открывают ворота продуктовой документации; штатный отбор применяется и после допоиска.
15. Retrieved-but-filtered и удалённые при упаковке контекста фрагменты не считаются доказательствами ответа.
16. Модель вернула неизвестный source ID, выдуманную цитату, невалидный JSON или сняла обязательность аспекта: результат отклоняется, LLM-repair не запускается.
17. Prompt injection внутри документа не меняет правила, инструменты, квоты и задачу пользователя.
18. Недоступный пользователю источник не попадает в оценку, допоиск, ответ, историю или видимую диагностику.
19. Уточнение задаётся только при влияющей на ответ неоднозначности и максимум один раз; известные сведения повторно не спрашиваются.
20. Timeout, cancellation и запоздалый результат на каждой новой стадии: нет зависания, второго terminal event, позднего синтеза или скрытого повторного вызова.
21. Ошибка записи новой диагностики/схемы не ломает базовый безопасный ответ; fallback не получает метку полного подтверждения.
22. Новые поля совместимы со старой историей и клиентом в поддерживаемом контракте; включение/выключение не требует удаления данных.
23. Общий лимит итогового синтеза равен одному; отдельные оценочные вызовы и исходные вызовы видны в общих счётчиках.
24. Семантическая оценка новых результатов не выполнена: простой факт наличия новых chunks не повышает аспект до `supported`.

В негативных сценариях проверяй не только статус, но и отсутствие запрещённого действия. Отдельно проверь frontend-компонент и contract serialization, не ограничивайся unit-тестом планировщика.

## 12. Проверка полезности и пределы выводов

Подготовь воспроизводимый offline replay текущего и нового маршрутов. Используй одинаковые исходные результаты, управляемые ответы дополнительных адаптеров, модель/версию prompt и набор доступных каналов. Сделай не менее 30 небольших размеченных синтетических сценариев по типам задач и отказов; отдели набор настройки от неизменяемого контрольного набора.

В каждом случае укажи вопрос, известный контекст, обязательные факты и источники, применимость, допустимость уточнения/частичного ответа и ожидаемое поведение. Разметка должна быть задана независимо от ответа тестируемого оценщика. Нельзя проверять достаточность только той же моделью, которая её назначила.

Метрики: покрытие обязательных аспектов; ошибочное подтверждение отсутствующих фактов; ошибки сущностей/версий; неправильные отказы и лишние уточнения; recovery адресным допоиском; вызовы и задержка. Показывай результаты по типам задач, а не только среднее. Синтетический replay проверяет механику, но не доказывает рост пользовательской удовлетворённости.

Для реального качества подготовь формат корпуса из 100–200 обезличенных пользовательских запросов с ручной разметкой и отдельным holdout. Не выдумывай такой корпус и не читай массово production-логи без разрешения. Если реальных данных нет, результат улучшения качества — `NOT_MEASURED`, с точным перечнем недостающего, а не PASS и не придуманное «+20%».

При последующем разрешённом сравнении на живых данных нужны одинаковое временное окно, совместимая ревизия корпуса, одинаковая модель и отсутствие кэша. Сохранённый replay явно называй replay, не свежим измерением. Смена ревизии источников между сравниваемыми прогонами делает сравнение несопоставимым.

## 13. Разрешённые проверки и сетевой бюджет этого задания

Без дополнительного явного разрешения: Hub — 0 вызовов, gateway — 0 вызовов, пилотная БД — 0 обращений. Все новые механизмы должны тестироваться через фикстуры/заглушки либо подтверждённые изолированные локальные ресурсы. Приложение, запускаемое для теста, тоже не должно автоматически опрашивать общий каталог Hub или отправлять фоновые запросы: отключи внешние адаптеры в test env и поставь сетевой tripwire.

Программные лимиты будущего пользовательского запроса не являются разрешением агенту нагружать общие службы при разработке.

Если к моменту выполнения владелец отдельно разрешил live-пробу, до её начала зафиксируй согласованный конкретный лимит Hub/gateway, уже сделанные вызовы и оставшийся бюджет. Выполняй обращения последовательно; остановись при исчерпании или общем сбое; повтор после таймаута не считай новой бесплатной попыткой. Не запускай всю live-группу тестов автоматически.

По `package.json` выбери существующие build/typecheck/lint/offline/acceptance-группы. Сначала собери contracts, затем затронутые приложения. Применение миграции и rollback проверяй только в явно изолированной тестовой БД NS2. Отдельно зафиксируй команды, exit codes и ограничения среды. SKIP не подменяет успешную проверку.

## 14. Порядок выполнения и выдаваемые файлы

После сверки состояния составь короткий план с конкретными найденными точками интеграции и продолжай реализацию, не останавливаясь на согласовании обычных деталей. Не запрашивай повторно известные пути и решения. Доступ к отсутствующему репозиторию, конфликтующие правки или необходимость запрещённого действия — блокеры соответствующей части, не повод выдумывать её содержание.

Рекомендуемый порядок: контракты и чистая логика → тесты → интеграция off/shadow → active-допоиск и fallback → минимальный UI/история → replay → сборка и отчёт. После каждого смыслового блока проверяй целевые тесты. Не распараллеливай правки одного файла между несколькими агентами.

> **Примечание R2.1:** места файлов и итоговые артефакты — по канону R2.1 (`TASK` / `REPORT` / `EVAL` / `PILOT_INSTRUCTIONS`); run logs/patches вне tracked tree.

## 15. Критерий готовности и финальный ответ агента

Задание готово к инженерной проверке, когда вертикальный срез реализован, отключается `off` без регрессии исходного пути, работает в shadow и active на фикстурах, соблюдает все квоты/границы, содержит реальные тесты и отчёт. Полезность на синтетике и инженерная готовность не равны готовности пилота.

> **Примечание R2.1:** итоговый ответ агента — по 11-пунктовому шаблону R2.1; engineering ready = P0+P1 green.

Начинай со сверки состояния, затем реализуй безопасную доступную часть задания. Не останавливайся на пересказе этого промпта и не делай неподтверждённых заявлений о внедрении.
